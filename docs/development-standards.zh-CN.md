# 开发标准

英文版： [development-standards.md](development-standards.md)

## 目的

这份文档记录 Viden 维护者和编码 agent 修改项目时应遵守的编码标准。

## 核心规则

- 变更应保持小、可审查、可回退。
- 除非任务明确要求改变行为，否则保留现有行为。
- 新增抽象前，优先复用已有模块、工具函数和代码风格。
- 优先删除和简化，而不是堆叠新层。
- 没有明确产品或工程理由时，不新增依赖。
- 把文档和代码注释视为实现的一部分。以后所有编码工作都必须让代码、维护者
  需要的注释，以及受影响的文档保持一致，否则不算完成。

## 必须遵守的编码标准：文档与注释

以后每一次代码变更都必须把文档和代码注释作为交付内容的一部分，而不是可选
的收尾清理：

- 动手前先判断这次变更是否可能影响用户可见行为、命令、配置、架构、工作流、
  打包方式或维护假设；
- 实现过程中，对不明显的设计决策、invariant、安全边界、协议兼容、终端渲染
  规则或并发行为，补充简洁的代码注释；
- 行为发生变化时，在同一个变更集中更新相关长期文档；如果存在对应的
  `*.zh-CN.md` 文档，也要同步更新；
- 交付前复查最终 diff，并说明文档和注释是已更新、原本足够，还是本次确实
  不需要。

如果代码改变了行为却留下过期文档或误导性注释，就不能视为完成。

## 代码变更完成定义

每一次代码变更都要同时补齐维护者上下文，否则不视为真正完成：

- 实现过程中就判断这次变更是否影响文档、注释，或两者都影响；不要把这件事
  推迟到单独的收尾清理；
- 当行为、命令、配置、截图、工作流、架构、打包或排障方式变化时，在同一个
  变更集中同步更新文档；
- 对不明显的 invariant、安全边界、渲染规则、协议兼容或并发行为，新增或
  更新必要的代码注释；
- 当实现变化导致旧注释或旧文档产生误导时，及时删除或改写；
- 注释要简洁，聚焦它保护的设计决策或约束；
- 在测试和交付前，把文档与注释复查纳入最终 diff 检查。

## 文档标准

当变更影响以下内容时，应在同一个变更集中同步更新相关文档：

- 用户可见的命令、参数、配置或安装步骤；
- TUI 行为、快捷键、面板、截图或工作流；
- 架构、模块边界、运行时契约或持久化格式；
- provider 行为、权限行为、工具语义或安全规则；
- 发布、打包、Homebrew 或问题排查说明。

根目录 README 保持聚焦，只写产品价值、安装、使用、反馈和授权信息。
长期保留的架构、计划和实现细节放在 `docs/` 目录下。

编辑长期保留的用户文档时，应尽量同步更新对应的简体中文 `*.zh-CN.md`
版本。如果确实无法在同一个变更里完成翻译，需要在 commit 或 PR 说明里
明确标记这个缺口。

文档必须描述当前已经实现的行为。不要把未来计划、占位面板、模拟数据或未经
验证的 provider 行为写成已完成能力。如果功能仍是部分实现，需要明确当前
限制和下一步预期。

## TUI 交互体验标准

以后新增的交互式设置、模式切换、provider/model 选择、权限选择、主题选择、
lane/agent 操作，以及其他需要用户决策的入口，默认都要采用 selector-first
交互模式：

- 打开可操作 picker，而不是只展示信息页；
- 多选项场景要支持搜索/过滤；
- 支持键盘选择和 `Enter` 应用；
- command palette 或 overlay 可见时，要支持鼠标选择；
- 显示当前值，并说明高亮动作会产生什么效果；
- 只有 `/config`、`/status`、`/provider doctor` 这类明确诊断、原始详情或状态命令，
  才应该保留为被动信息页。

如果未来某个功能无法使用这套模式，需要在设计文档或代码注释里先说明原因，
再交付。

## 代码注释标准

注释用于解释代码本身无法清楚表达的意图：

- 后续修改必须保持的 invariant；
- 安全或权限边界；
- 协议、transcript、持久化或 provider 兼容性契约；
- 不明显的控制流、终端渲染行为或并发规则；
- 为什么某个看似更简单的实现是错误的。

避免只复述下一行代码含义的注释。优先使用清晰命名和小函数；当命名不足以
保护后续维护者避开隐蔽错误时，再添加注释。

完成代码变更前，需要检查 diff 并回答两个问题：

- 六个月后的维护者能否理解这个行为为什么存在？
- 这次改动是否改变了需要写入文档的用户可见契约？

如果答案是肯定的，应在同一个变更集中补上最小但有用的注释或文档更新。

## 验证标准

声明完成前，先运行最小但有意义的验证；当变更触及共享行为时，再扩大验证范围：

- Rust 代码变更需要格式化检查；
- 变更模块需要聚焦测试；
- 发布相关或共享运行时变更需要 workspace 测试；
- 视觉变更需要生成 TUI preview 或截图；
- 命令、工作流或公开行为变更需要复查文档。

如果某些内容没有测试，需要在最终说明或 commit trailer 中诚实记录。
