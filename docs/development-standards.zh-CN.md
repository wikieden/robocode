# 开发标准

英文版： [development-standards.md](development-standards.md)

## 目的

这份文档记录 RoboCode 维护者和编码 agent 修改项目时应遵守的编码标准。

## 核心规则

- 变更应保持小、可审查、可回退。
- 除非任务明确要求改变行为，否则保留现有行为。
- 新增抽象前，优先复用已有模块、工具函数和代码风格。
- 优先删除和简化，而不是堆叠新层。
- 没有明确产品或工程理由时，不新增依赖。
- 把文档和代码注释视为实现的一部分，而不是可选的收尾工作。

## 文档标准

当变更影响以下内容时，应在同一个变更集中同步更新相关文档：

- 用户可见的命令、参数、配置或安装步骤；
- TUI 行为、快捷键、面板、截图或工作流；
- 架构、模块边界、运行时契约或持久化格式；
- provider 行为、权限行为、工具语义或安全规则；
- 发布、打包、Homebrew 或问题排查说明。

根目录 README 保持聚焦，只写产品价值、安装、使用、反馈和授权信息。
长期保留的架构、计划和实现细节放在 `docs/` 目录下。

编辑长期保留的用户文档时，应尽量同步更新对应的简体中文 `*.zh-CN.md`
版本。如果确实无法在同一个变更里完成翻译，需要在 commit 或 PR 说明里
明确标记这个缺口。

## 代码注释标准

注释用于解释代码本身无法清楚表达的意图：

- 后续修改必须保持的 invariant；
- 安全或权限边界；
- 协议、transcript、持久化或 provider 兼容性契约；
- 不明显的控制流、终端渲染行为或并发规则；
- 为什么某个看似更简单的实现是错误的。

避免只复述下一行代码含义的注释。优先使用清晰命名和小函数；当命名不足以
保护后续维护者避开隐蔽错误时，再添加注释。

## 验证标准

声明完成前，先运行最小但有意义的验证；当变更触及共享行为时，再扩大验证范围：

- Rust 代码变更需要格式化检查；
- 变更模块需要聚焦测试；
- 发布相关或共享运行时变更需要 workspace 测试；
- 视觉变更需要生成 TUI preview 或截图；
- 命令、工作流或公开行为变更需要复查文档。

如果某些内容没有测试，需要在最终说明或 commit trailer 中诚实记录。
