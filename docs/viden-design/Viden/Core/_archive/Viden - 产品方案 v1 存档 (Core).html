01定位与核心论点 Positioning

一句话：Viden 是 agent 团队的驾驶舱 —— 多个不同 agent（codex / claude-code / kiro / 内置）在同一工程里分工并行，人评审它们的行为，给行为上闸。

机器人怕炸电机，ML 怕分数回退，游戏怕手感变坏 —— 都是"行为"问题，代码 diff 看不出来。Viden 评审行为、给行为上闸；领域差异只是证据的形态和闸的类型。 Agents change behavior, not just code. Viden reviews behavior and gates behavior.

与参照物的分野：Zed 解决人与人实时共编文本（agent 时代该假设已弱化）；WorkBuddy 解决一人指挥多 agent 办公（无"多个人"概念，无工程纵深）；Cursor/Windsurf 只有代码 diff（无行为证据）。Viden 的空白地带：N 个人 × M 个 agent × 一个工程，异步、闸驱动、可审计。

02概念模型（定稿） Conceptual Model

Project 工程 一个 git 仓库 └─ Lane 泳道 角色工位：agent 长期坐镇，独立 worktree + 分支 ├─ Session 会话 lane 内一次具体任务，可多开并行 │ └─ Subagent 会话内编排的下级（planner / editor / test…） ├─ Worktree 工作树 该 lane 专属的工作目录 └─ Target 执行目标 命令在哪跑：本地 / SSH 远程（机器人主控板、多卡主机）/ 仿真实例 跨 lane 协作四原语（产物穿边界必经 ⏸ 闸） 交接 handoff · 评审请求 review request · 契约 contract · 依赖 dependency

已定稿的三个决策（见协作机制图）：① 每 lane 独立 worktree，集成闸合并，冲突退回原 lane；② 评审是动作不是角色，任何 lane 可向任何 lane 发起；③ V1 由人手动编排（点交接、批闸），自动编排（orchestrator lane）留到 V2。

本方案新增第五原语：验证 Validation —— 闸的前置条件由领域包提供的 runner 自动执行（跑仿真 / 跑 eval / 跑回放回归），结果作为证据挂在闸上。闸 = 自动验证 + 人工批准，二者缺一不可。

03架构判断：内核 + 领域包 Core + Domain Packs

三个领域的需求不在内核里写死，而是抽象成一个扩展点：领域包 Domain Pack。内核只认识 lane / 闸 / 证据 / 契约；领域包向内核注册四样东西：

领域包还可挂载 skill 库：lane 创建时选"角色 + agent + skill 包"。游戏包首发直接挂 MuseGameWorkshop（14 个 P0 skills + 27 个模板 + review gate / evidence 目录约定）—— 它的 templates/production/review-gate.md 和 docs/evidence/ 与 Viden 的闸、证据是同一套思想，Viden 把它从"文档纪律"升级为"产品强制"。

首发领域包选游戏。理由：① 已有 MuseGameWorkshop 资产与 Godot 示例工程可直接验证；② 反馈环最快、无硬件依赖（机器人需要实机/仿真环境，ML 需要算力）；③ 画廊评审、回放证据等界面形态最丰富，能把"行为评审"的故事讲透。机器人包与 ML 包在 V1.x 以同一扩展点跟进。

04V1 范围 Scope

V1 是单机单人版本：一个开发者 + 一队 agent。团队能力在 V1.5（见 06 节），但 V1 的技术选型必须为它铺路（lane 以 daemon 形态运行，驾驶舱只是视图）。

优先级能力内容
P0Lane 内核lane 创建（角色 + agent + skill 包 + 闸策略）；ACP 接入 codex / claude-code / kiro + 内置 agent；worktree 自动管理；session 多开；状态机 run / wait / gate / done
P0执行目标抽象lane 绑定 target：V1 实现 local + SSH 远程（持久会话、断线重连、命令队列）；代码同步策略（远程 worktree / rsync）；端口转发（tensorboard / foxglove 回传）；证据从目标采集回拉。机器人 / ML 开发都是远程连目标机，抽象必须在 V1 内核
P0四原语 + 验证交接、评审请求、契约（contracts/ 目录 + 修改走闸）、依赖（阻塞/解锁）、闸前自动验证
P0闸系统闸定义、前置验证、批/驳/退回；闸策略即代码（仓库内声明式规则，如 contracts/** → 强闸）；V1 审批人都是自己
P0行为 Diff 评审评审视图 = 代码 diff + 行为证据并排；证据自动写回 docs/evidence/（git-native，可审计）
P0游戏领域包Godot headless runner；试玩回放证据；回放回归闸；数值契约；画廊评审；挂载 MuseGameWorkshop skills
P0集成闸多 lane 分支 → diff review → 人工合并 → main；冲突退回原 lane
P1游戏包增强金样画面闸、帧预算闸、手感调参会话（实时滑杆 → agent 写回终值）
P1ML 包训练 lane（长任务 + loss 缩略图）、eval 闸、checkpoint/数据集 artifact
P1机器人包仿真 lane、分级实机闸（sim/bench/field）、遥测证据、设备占用锁
P1团队基础闸收件箱、lane 认领/移交、团队时间线（详见 06）
P2V2 候选orchestrator lane 自动编排、旁观/接管、IM 批闸、token 预算治理、Unreal runner、创意 AI 工具接入（生图/音频/3D 走资产闸）

创意 AI 工具（ComfyUI / 音乐生成 / 3D 生成）刻意放到 P2：MuseGameWorkshop 的 asset brief / provenance / review 流程先以模板 + 闸的形式跑通，工具直连是之后的事 —— 先有闸，再接生成。

05三个领域包规格 Domain Pack Specs

游戏包 V1 首发GAME

典型 lane 团队：策划（claude · GDD/数值契约）· gameplay（codex）· 渲染/VFX（kiro）· 内容生成（内置）

  • 试玩即证据：headless 试玩 → 回放视频挂 patch
  • 回放回归：确定性输入回放做行为单测
  • 画廊评审：批量生成内容 keep / kill
  • 数值契约：碰平衡表必走策划闸
  • skill 库：MuseGameWorkshop 直挂
闸：回放回归 ⏸ · 金样画面 ⏸ · 帧预算 ⏸
runner：Godot headless（P0）→ Unreal（P2）
ML 包 V1.xML / AI

典型 lane 团队：数据（清洗/版本）· 训练（长任务 lane）· 评测（eval harness）

  • 训练 lane：8 小时任务常驻，卡片显示 loss 缩略图 + GPU
  • 远程多卡主机：lane 绑 SSH target，GPU 槽位租约，tensorboard 端口回传
  • needs-input 特化："loss 发散，回滚 ckpt？"
  • 实验交叉评审：eval 结果互评，胜者进契约
  • artifact 扩展：checkpoint / 数据集版本
闸：eval 不回退 ⏸ · 数据集变更 ⏸
runner：eval harness / benchmark 套件
机器人包 V1.xROBOTICS

典型 lane 团队：感知 · 规划/控制 · 仿真验证；与 RoboCode CLI 同源生态

  • 分级实机闸：sim 自由 → bench 轻闸 → field 强闸 + e-stop 前置
  • 仿真 lane：lane 绑仿真实例，回放进证据
  • 远程上板：SSH 连主控板开发，断线续会话；RoboCode（Rust）足够轻可直接上 ARM 板
  • 行为 diff：PID 改动旁边放阶跃响应曲线
  • ROS 契约：.msg / URDF 变更自动告警依赖方
  • 设备占用锁：实机时间片 lease
闸：仿真通过 ⏸ · 实机分级 ⏸⏸
runner：MuJoCo / Isaac / Gazebo

06团队协作（V1.5） Team

核心立场：当代码由 agent 写，人和人协作的对象从文本变成决策。不做同步共编（Zed 的核心），不做 IM 聊天机器人（WorkBuddy 的核心）；做异步、闸驱动的混合团队（人 + agent 同为"工位"）。

闸收件箱 gate inbox闸按策略指派到人（数值契约 → 主策划）；每人一个跨 lane 待批队列，批闸看到行为 diff + 证据。团队日常 = 清闸队列V1.5
认领 / 移交 claim / handoverlane 可移交同事、夜间自动驾驶（闸积压到早上）。前提：lane 以 headless daemon 运行，驾驶舱只是视图 —— V1 架构已按此设计V1.5
团队时间线 timeline谁批了哪个闸、哪条 lane 产出什么、契约第几版谁改 —— git-native 审计流，企业合规卖点V1.5

IM 批闸企微/飞书只推闸通知 + 一键批/驳，不在 IM 干活（与 WorkBuddy 反向收窄）V2

信息如何在人和 agent 之间流动

同一份变更通告走双通道，按接收者形态投递：

  • 送到人：进闸收件箱 / 定期简报（V2 起可转发 IM）—— 人读摘要、做决策；
  • 送到 agent：写成备忘 memo 注入对方 lane 的工作上下文（memos/ 目录，session 启动必读）。agent 必须 ack，并自行决定动作：rebase、更新调用方、或向变更方发起评审请求 —— agent 收到的不是聊天消息，是上下文补丁。

例：codex lane 改了 contracts/tech-plan.md 的接口章节 → 书记官识别出 kiro lane 依赖该契约 → kiro 的下一个 session 启动时上下文里已有这份变更备忘，它主动 rebase 并回 ack；同时负责人会在当天简报里看到这条变更和 kiro 的响应状态。

08非目标 Non-goals

  • 不做游戏引擎、训练框架、仿真器 —— 只做它们的 runner 接入和证据呈现。
  • 不做同步共编、不做 IM 内对话式干活。
  • 不做"一键生成完整游戏/完整机器人"叙事；不鼓励绕闸（与 MuseGameWorkshop 的"不要这样用"一致）。
  • V1 不做自动编排 —— 先让手动协作的每一步都可信，再谈自动化。
  • 不自研模型，模型与 CLI 均为可插拔（ACP / 内置双轨已定）。

09验收场景 Acceptance

V1 验收用一个真实小项目跑通全链路 —— 直接用 MuseGameWorkshop 的 Boss Rush《反击试炼》：

  • 3 条 lane（claude 策划 / codex gameplay / kiro 渲染）从 pitch 到可试玩 demo，全程在 Viden 内完成；
  • 设计契约、技术方案交叉评审、回放回归闸、集成闸各至少走通一次；
  • docs/evidence/ 自动累积全部证据，事后可完整复盘"每个行为改动是谁批的、凭什么批的"；
  • 评审一次行为 diff 的平均耗时 < 评审同等代码 diff（证据让评审更快，而不是更繁琐）。

10待决策问题 Open Questions

Q1闸策略文件的格式与位置

建议仓库根 viden.toml（RoboCode 同源 Rust 生态，TOML 自然），声明闸类型、路由规则、领域包启用。备选：YAML / 沿用 AGENTS.md 章节。

Q2契约的载体

建议 Markdown + frontmatter（人可读、git 可 diff、MuseGameWorkshop 模板可直接复用），结构化校验由领域包的 schema 做。备选：纯结构化（JSON/TOML）。

Q3回放证据的格式

视频文件（直观但重、git 不友好）vs 确定性输入序列 + 实时重演（轻、可交互，但要求引擎确定性）。建议双轨：闸用输入序列，评审 UI 现场重演。

Q4kiro 的 ACP 成熟度

三个首发 CLI 中 kiro 的 ACP 桥接需要验证；不行则 V1 先 codex + claude-code，kiro 走终端适配。

Q5命名

Lane 保留英文已定；产品内"领域包"对外叫 Domain Pack 还是直接叫"游戏模式/机器人模式"？影响首页叙事，可后定。

Q6闸决策日志的可训练格式

闸数据飞轮的前提：V1 起把每次闸决策（diff + 证据 + 批/驳 + 理由）按可训练格式落盘（opt-in），为评审者模型微调做准备。格式待定。

Q7远程 target 的代码同步策略

远程 worktree（git 在目标机上）vs rsync 推送（板子友好但失去 git 语义）vs agent 直接装在目标机（多卡主机可行，ARM 板看 RoboCode 体积）。可能需要按目标类型双轨。

11模型与工具层 Models & Tools

总原则：弱模型 + 强验证。验证 runner 和闸的存在降低了对模型的要求，大多数需求不该用微调解决。模型层分三档：

档位适用说明
不动模型协作原语遵从、工程规范、配置生成prompt + skill 库 + schema 约束解码 + 校验器兜底
小模型路由书记官简报、通告分类路由、证据摘要、闸前预检调用量最大、智能要求最低；含团队隐私 → 可本地部署。模型路由策略 V1 内建（整理用小模型、实现用强模型的团队级配置）
值得微调仅三个点，见下其余一律先问：prompt + 验证能不能兜住

三个微调方向

  • Godot 4 / GDScript 域适配（游戏包）：通用模型大量混淆 Godot 3/4 API，GDScript 语料少。LoRA 成本最低、收益最确定，作内置 lane 的游戏特化选项。
  • ROS2 / 控制代码域适配（机器人包）：物理单位、坐标系（TF 方向）、实时约束是通用模型弱项。仿真闸已兜住安全，微调是提一次通过率、省 token。
  • 评审者模型（战略级）：闸在天然生产标注数据 —— 每次闸决策 = 一条样本（diff + 证据 + 批/驳 + 理由）。用它微调闸前预审模型，是纯代码工具们没有的数据资产。V1 先落盘（Q6），微调放 V2。

明确不微调：曲线读图（loss 发散 / 遥测异常 / 超调）用经典检测器做，LLM 只负责解释结果。

工具接入：ACP 给 agent，MCP 给工具

Lane ├─ ACP → 完整 agent（codex / claude-code / kiro） 已定 ├─ MCP → 工具（godot-mcp、第三方/购买工具、ROS/实验跟踪） 新增正式层 └─ Validation Runner → 闸前验证（必须第一方）
  • MCP 工具受闸策略管：lane 创建时声明工具白名单，每次调用进审计流，产物照走证据。买来的工具不可信任，但闸在自己手里。
  • 验证 runner 不外包：agent 干活可用任何 MCP 工具，但闸前验证由第一方 headless 调用执行，否则闸的可信度被外包。
  • 机器人包接 ROS / 仿真工具、ML 包接实验跟踪工具时，复用同一白名单 + 审计机制。

通过本方案后，设计顺序建议：D2 行为 Diff 评审（三领域三形态）→ D3 闸审批流 → D1 主视图修订 → D4 创建流程。术语全表见此前对话定稿的中英对照。
